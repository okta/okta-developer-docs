#### Authentiation settings

5. Specify authentication settings to your app resources.

| Property | Description |
|----------| -------------|
| **Authentication mode** `*` | Select the authentication mode to make outbound calls to your SCIM server. <br> <ul><li> **Header**: Uses authorization header with a customer-provided token in the following format: `Authorization: {API token}` </li><li> **Bearer**: Uses authorization header with a customer-provided bearer token in the following format: `Authorization: Bearer {API token}`</li><li> **OAuth 2**: Uses OAuth 2.0. Select a grant type.</li> </ul> **Note**: Basic authentication isn't supported for SCIM. See [SCIM integration limitations](/docs/guides/submit-app-prereq/main/#scim-integration-limitations).  |
| **Grant type** | Select the OAuth 2.0 grant type that your SCIM server uses: <ul><li> **Authorization Code** (default): Redirects the user to sign in to the identity provider and grant consent before returning an authorization code. Requires an authorize endpoint, client ID, and client secret, which apply at the integration level for all orgs that install your integration. </li><li> **Client Credentials**: Your app authenticates directly with its own credentials in a machine-to-machine call. There's no redirect, sign-in, or consent step. Only the token endpoint and scopes are specified at the integration level. The client ID and client secret aren't collected here. Each org admin specifies their own values for their app instance when they enable API integration in the **Provisioning** tab. </li></ul> |
| **Authorize endpoint** | Required for the **Authorization Code** grant type. Specify the HTTPS authorize endpoint. For example: `https://myexample.com/oauth2/auth`<br> You can specify a dynamic endpoint URL. See [Dynamic properties with Okta Expression Language](#dynamic-properties-with-okta-expression-language). |
| **Token endpoint** | Required for both grant types. Specify the HTTPS token endpoint. For example: `https://myexample.com/oauth2/token`<br>You can specify a dynamic endpoint URL. See [Dynamic properties with Okta Expression Language](#dynamic-properties-with-okta-expression-language). |
| **Client ID** | Required for the **Authorization Code** grant type. Specify the client ID.|
| **Client secret** | Required for the **Authorization Code** grant type. Specify the client secret. |
| **Scopes** | Optional: Specify scopes. Applies to both grant types. |

> **Note:** The Client Credentials grant type doesn't collect a client ID or client secret in the OIN Wizard. In the Authorization Code flow, Okta redirects the user to sign in to the identity provider and grant consent before Okta and your app exchange a token. This extra step means every app instance can safely share the same client ID and client secret. The Client Credentials flow skips that step and makes a direct machine-to-machine call, so each app instance needs its own client ID and client secret. The org admin sets the client ID and client secret for their app instance in the Admin Console. Go to **Applications** > **Applications** > *your app instance* > **Provisioning** > **Configure API Integration** > **Enable API integration**.

6. Click **Configure your integration**.
