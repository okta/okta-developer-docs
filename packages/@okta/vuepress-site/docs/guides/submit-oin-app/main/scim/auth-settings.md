#### Authentiation settings

5. Specify authentication settings to your app resources.

| Property | Description |
|----------| -------------|
| **Authentication mode** `*` | Select the authentication mode to make outbound calls to your SCIM server. <br> <ul><li> **Header**: Uses authorization header with a customer-provided token in the following format: `Authorization: {API token}` </li><li> **Bearer**: Uses authorization header with a customer-provided bearer token in the following format: `Authorization: Bearer {API token}`</li><li> **OAuth 2**: Uses OAuth 2.0. Select a **grant type**.</li> </ul> **Note**: Basic authentication isn't supported for SCIM. See [SCIM integration limitations](/docs/guides/submit-app-prereq/main/#scim-integration-limitations).  |
| | OAuth 2.0 settings |
| **Grant type** | Select the OAuth 2.0 grant type that your SCIM server uses: <ul><li> **Authorization Code** (default): Your app authenticates on behalf of a signed-in user. Requires an authorize endpoint, client ID, and client secret, which apply at the integration level for all orgs that install your integration. </li><li> **Client Credentials**: Your app authenticates directly with its own credentials in a machine-to-machine call. There's no redirect, sign-in, or consent step. Only the token endpoint and scopes are specified at the integration level. The client ID and client secret aren't collected here — each org admin specifies their own values for their app instance when they enable API integration. </li></ul> |
| **Authorize endpoint** | Required for the **Authorization Code** grant type. Not shown for **Client Credentials**. Specify the HTTPS authorize endpoint. For example: `https://myexample.com/oauth2/auth`<br> You can specify a dynamic endpoint URL. See [Dynamic properties with Okta Expression Language](#dynamic-properties-with-okta-expression-language). |
| **Token endpoint** | Required for both grant types. Specify the HTTPS token endpoint. For example: `https://myexample.com/oauth2/token`<br>You can specify a dynamic endpoint URL. See [Dynamic properties with Okta Expression Language](#dynamic-properties-with-okta-expression-language). |
| **Client ID** | Required for the **Authorization Code** grant type. Specify the client ID. Not shown for **Client Credentials** — see note. |
| **Client secret** | Required for the **Authorization Code** grant type. Specify the client secret. Not shown for **Client Credentials** — see note. |
| **Scopes** | Optional: Specify scopes. Applies to both grant types. |

> **Note:** For the **Client Credentials** grant type, the client ID and client secret aren't specified in the OIN Wizard. In the authorization code flow, a user is redirected to sign in and grant consent before Okta and your app exchange tokens, which adds a layer of security even when all instances share one client ID and client secret. The client credentials flow has no sign-in or consent step, so each app instance requires its own unique client ID and client secret — otherwise, a credential breach on one instance would expose every instance that shares those credentials. Each org admin provides their own client ID and client secret for their app instance in the Admin Console at **Applications** > **Applications** > *your app instance* > **Provisioning** > **Configure API Integration** > **Enable API integration**.
